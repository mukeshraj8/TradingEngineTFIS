# TFIS Phase 3B Business Engine Framework

Date: Wednesday, July 29, 2026

## Verdict

`PHASE_3B_ACCEPT`

Phase 3B creates the generic Business Engine Framework without migrating S21,
S23, Gap, Entry, Strike, Target, MSL, TSL, APS, paper, live, replay, or broker
runtime behavior.

## Why Business Engines Exist

Policies answer one narrow question inside a decision flow. Business engines
represent reusable TFIS capabilities with explicit contracts, dependencies,
validation, evidence, quality, and performance expectations.

An engine is the reusable business capability. A policy is one executable rule
choice that may later be hosted by an engine.

Examples:

- Market Structure Engine
- Monthly Status Engine
- Gap Engine
- Entry Engine
- Contract Selection Engine
- Risk Engine
- Lifecycle Engine
- Execution Intent Engine

## Contract Location

The generic immutable contracts live in:

- `src/tfis/domain/business_engine.py`

The initial metadata-only catalog lives in:

- `config/business_engines/catalog.yaml`

The catalog report is generated by:

- `scripts/run_phase3b_business_engine_report.py`

The report artifact is:

- `reports/phase3b/business_engine_report.json`

## Engine Contract

Each `BusinessEngineDefinition` declares:

- engine identity
- display name and purpose
- stage
- schema version
- required inputs
- optional inputs
- produced outputs
- evidence outputs
- validation rules
- failure modes
- quality metrics
- state requirements
- dependencies
- required capabilities
- provided capabilities
- supported products
- supported strategy families
- performance contract

Definitions are frozen dataclasses. Sequence fields are normalized to immutable
tuples and the registry exposes definitions through a read-only mapping.

## Execution Lifecycle

The common execution model is:

1. `BusinessEngineContext`
2. `BusinessEngineInput`
3. validation
4. execution
5. `BusinessEngineEvidence`
6. quality assessment
7. `BusinessEngineResult`
8. decision engine consumption

The base `BusinessEngine.validate()` method delegates to
`validate_business_engine_invocation()`, which fails closed for missing inputs,
unsupported product, unsupported strategy family, missing capabilities,
missing configuration hash, missing required state, and timestamp type
inconsistency.

Phase 3B does not provide runtime orchestration. Engine execution remains a
future migration step.

## Result Contract

`BusinessEngineResult` supports:

- status
- quality
- optional confidence
- warnings
- errors
- evidence
- intermediate values
- execution metrics
- validation result
- processing duration through metrics
- input completeness
- capability usage
- dependency versions through metrics
- provenance

Confidence is optional and must be between 0 and 1 only when supplied. Engines
that do not define confidence leave it as `None`.

## Evidence Contract

`BusinessEngineEvidence` is first-class and supports:

- raw evidence references
- derived evidence references
- formula references
- requirement references
- intermediate values
- quality notes
- data warnings
- missing inputs
- provenance

`BusinessEngineEvidence.to_decision_evidence_fragment()` produces a deterministic
fragment that can be carried alongside existing `TFISDecisionEvidencePacket`
audit compatibility data during migration.

## Capability Model

Capabilities are explicit through `BusinessEngineCapability`:

- `MONTHLY_STATUS`
- `MARKET_STRUCTURE`
- `OPTION_CHAIN`
- `STRIKE_SELECTION`
- `PREMIUM_REFERENCE`
- `OI_REFERENCE`
- `ENTRY`
- `GAP`
- `MISSED_ENTRY`
- `TARGET`
- `MSL`
- `TSL`
- `APS`
- `EXECUTION`
- `POSITION_STATE`
- `RISK`
- `LIFECYCLE`
- `EXECUTION_INTENT`

Engines declare required and provided capabilities. The registry validates that
required capabilities are provided by declared dependencies; support is never
inferred from names or stage order.

## Dependency Graph

The initial catalog defines this deterministic graph:

```text
market_structure
  -> monthly_status
    -> gap
      -> entry
        -> contract_selection
          -> risk
            -> lifecycle
              -> execution_intent
```

The registry builds a deterministic topological order and rejects unknown or
circular dependencies.

## Registry Design

`BusinessEngineRegistry` is:

- immutable after initialization
- deterministic
- thread-safe for reads after initialization
- fail-closed on duplicate IDs
- fail-closed on unknown dependencies
- fail-closed on circular dependencies
- fail-closed on unsatisfied dependency capabilities
- independent of runtime modules
- independent of S21/S23 legacy strategy code

## Initial Catalog

The Phase 3B catalog contains placeholder definitions for:

- Market Structure Engine
- Monthly Status Engine
- Gap Engine
- Entry Engine
- Contract Selection Engine
- Risk Engine
- Lifecycle Engine
- Execution Intent Engine

These are contracts only. They do not implement Gap, Entry, Strike, Target,
MSL, TSL, APS, execution, broker integration, or runtime orchestration.

## Product Support

Each engine explicitly declares supported `TFISProductType` values:

- `FUTURES`
- `OPTION_SELLING`
- `OPTION_BUYING`
- `EQUITY`

Commodity support is a future-proof architecture goal, but the current
`TFISProductType` enum does not yet include `COMMODITY`. Phase 3B does not add
that enum value because it would be a broader product-contract migration.

## Decision Engine Integration

The framework is designed to sit before or beside `TFISDecisionEngine` during a
future migration. Business engines can produce validated outputs, capabilities,
quality notes, metrics, and evidence fragments that a decision engine can
consume. Phase 3B does not wire this into active runtime paths.

## Evidence Packet Integration

The existing `TFISDecisionEvidencePacket` remains the decision evidence
contract. Business engine evidence converts to a deterministic fragment and can
be carried through audit compatibility payloads while migration is staged. A
future phase can promote selected fragments into first-class packet sections
after the first engine migration proves the shape.

## Performance Contract

Each definition declares:

- expected execution frequency
- expected input size
- cacheability
- determinism
- parallel safety
- statefulness
- criticality

No optimization is implemented in Phase 3B. The metadata exists so future
orchestration can make explicit cache, scheduling, and safety decisions.

## Tests

Phase 3B adds tests for:

- deterministic registry loading
- immutable definitions and registry mapping
- duplicate detection
- unknown dependency validation
- capability validation
- circular dependency detection
- invocation validation
- result contract with optional confidence
- evidence fragment compatibility with decision evidence audit data
- architecture boundary against runtime, broker, and legacy strategy imports

## Future Migration Plan

Recommended migration order:

1. Market Structure Engine
2. Monthly Status Engine
3. Gap Engine
4. Entry Engine
5. Contract Selection Engine
6. Risk Engine
7. Lifecycle Engine
8. Execution Intent Engine

Each migration should move one capability at a time behind the generic
contract, prove parity against existing evidence, and keep active runtime
activation behind an explicit later change.

## Recommended Phase 3C

Phase 3C should migrate the first low-risk business capability into the
framework, preferably Market Structure or Monthly Status. The phase should add
one concrete engine implementation, parity fixtures, evidence packet mapping,
and orchestration tests while keeping paper/live runtime activation disabled
until separately reviewed.
